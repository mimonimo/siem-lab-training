침해 웹서버 로그 분석 실습 교안

여러 종류의 보안 로그를 Wazuh SIEM으로 분석해, 정상 트래픽 속에 숨은 침해 흔적을 시간·IP·계정으로 연결하고, 실제 침해와 미끼(정찰·정상업무·방어성공)를 구분하는 CTF형 실습입니다. 배경지식이 없어도 따라올 수 있도록 구성도·시나리오·로그 읽는 법·분석 방법·실전 쿼리까지 담았습니다.

① 구성도② 시나리오③ 로그 소스 ④ 로그 라인 해부⑤ 분석 방법론⑥ Wazuh 실전 ⑦ 실전 예제⑧ MITRE ATT&CK⑨ 탐지 룰 ⑩ 주의점·오탐⑪ 용어집

1네트워크 · 시스템 구성도

이 실습 서버 한 대에 웹서버·로그·SIEM·문제풀이 포털이 모두 올라가 있습니다.

공격자는 인터넷에서 방화벽을 거쳐 웹서버(Apache)에 접근하고, 웹서버의 모든 활동은 7종 로그로 남아 로컬 Wazuh 에이전트가 수집합니다. 학생은 포털에서 문제를 받아 Wazuh 대시보드로 분석합니다.

2침해 시나리오

하나의 로그 뭉치에 여러 사건이 섞여 있습니다. 일부는 이어지는 공격 체인, 일부는 판단력을 시험하는 미끼입니다.

#스토리라인성격핵심 로그
ASSH 브루트포스 → 웹셸(search.php) → 페이로드 다운로드 → cron 지속성 → /usr/bin/backup 변조체인auth · access · audit · cron
B야간 sudoers.d 백도어 등록 (NOPASSWD 권한 상승) — A와 동일 공격자체인auth · audit
E파일 압축(tar) 후 외부 유출(curl → 198.51.100.47) — 체인의 마지막체인access · audit
C스캐너 정찰 (sqlmap UA, 다수 404, 방화벽 포트스캔 차단) — 실제 침해 아님미끼access · error · ufw
D정상 관리자(opsadmin)의 야간 배포 cron — 공격처럼 보이나 정상미끼auth · cron
F반복 로그인 실패 후 계정 잠금 — 방어가 작동, 대응 불필요미끼auth

공격 체인 상세 (A → B → E)

  1. 최초 침투 (A1) — 공격자 198.51.100.23가 root·admin·oracle 등으로 다수 로그인 실패 후, webadmin 계정 인증에 성공합니다. auth.log에 "여러 Failed password 후 Accepted password"로 남습니다.
  2. 웹셸 배치 (A2) — /tmp에 만든 search.php를 sudo로 웹 루트(/var/www/html)에 복사합니다. auth.log의 sudo 기록 + auditd 파일변경으로 흔적이 남습니다.
  3. 원격 명령 실행 (A3) — 웹셸에 ?cmd=id, ?cmd=whoami 처럼 URL 파라미터로 명령을 보냅니다. access.log에 cmd= 요청이, audit에 프로세스 실행이 남습니다.
  4. 페이로드 다운로드 (A4) — 웹셸로 wget을 실행해 악성 파일을 /tmp/.cache/kworker로 내려받습니다.
  5. 지속성 (A5) — crontab에 매분·재부팅 실행을 등록해 재접속 없이도 살아남게 합니다.
  6. 바이너리 변조 (A6) — 시스템 명령처럼 보이는 /usr/bin/backup을 심어둡니다(setuid).
  7. 권한 상승 (B) — 야간에 /etc/sudoers.d/webadmin에 NOPASSWD 백도어를 등록해 상시 root를 확보합니다(동일 공격자).
  8. 정보 유출 (E) — tar로 파일을 압축(/tmp/loot.tgz)한 뒤 curl로 198.51.100.47에 업로드합니다. 체인의 종착점입니다.
미끼는 왜 있나 — 실무 SOC는 알림·이상 로그가 나와도 "정말 대응이 필요한가"를 판단합니다. C(정찰)·D(정상 관리자)·F(방어 성공)는 흔적이 남아도 대응이 불필요한 사례로, 이를 걸러내는 훈련입니다.

로그무엇이 보이나의심 포인트

4로그 라인 해부 — 한 줄씩 뜯어보기

각 로그 포맷의 구조를 알면 어디를 봐야 할지 바로 보입니다.

웹 접근 로그 (Apache Combined)

198.51.100.23 - - [13/Aug/2026:04:43:17 +0900] "GET /search.php?cmd=id HTTP/1.1" 200 90 "-" "curl/7.81.0"
└출발지 IP         └요청(경로+파라미터)        └상태  └크기      └User-Agent

빨강 출발지 IP, 파랑 요청 경로(여기에 cmd=가 있으면 웹셸), 초록 상태코드, 노랑 User-Agent(sqlmap·curl 등 도구 식별).

인증 로그 (sshd)

Aug 13 04:38:17 siem sshd[22050]: Accepted password for webadmin from 198.51.100.23 port 51060 ssh2
Aug 13 04:38:05 siem sshd[22004]: Failed password for invalid user oracle from 198.51.100.23 port 51002 ssh2
     └시각         └호스트  └데몬        └성공/실패          └계정         └출발지 IP

같은 IP에서 Failed 여러 번 → Accepted 패턴이 브루트포스 성공입니다. "invalid user"는 존재하지 않는 계정 시도.

감사 로그 (auditd)

type=SYSCALL ... comm="wget" exe="/usr/bin/wget" ... key="webshell_exec"
                실행된 명령          실행파일                     감사 규칙 태그

comm=은 실행된 명령, key=는 우리가 심은 감사 규칙 태그(webshell_exec/priv_esc/cron_persist/bin_tamper)로 의미를 바로 알 수 있습니다.

5분석 방법론 — 어떻게 접근하는가

  1. 기점 잡기 — 인증 로그에서 "다수 실패 후 성공"을 찾아 최초 침투 시각·IP·계정을 확정합니다.
    data.srcip:"198.51.100.23" and rule.groups:authentication_success
  2. 피벗(pivot) — 그 IP/계정을 필터해 같은 주체의 다른 행위를 모읍니다.
    data.srcip:"198.51.100.23"
  3. 시간축 연결 — 웹셸 배치 → 명령 실행 → 다운로드 → 지속성 → 변조 → 권한상승 → 유출을 시간순으로 잇습니다. 각 로그 줄에 찍힌 실제 시각(예: Aug 13 10:11:32, access.log의 [13/Aug/2026:10:16:32])을 읽어 배열하세요. ※ Discover의 Time 컬럼은 수집(적재) 시각이라 사건 순서와 다를 수 있으니, 순서 판단은 로그 본문의 시각으로 합니다.
  4. 교차 확인 — access.log의 요청과 audit.log의 프로세스 실행을 같은 시각으로 대조해 "정말 실행됐는지" 확인합니다.
  5. 미끼 걸러내기 — 이상 로그가 실제 침해로 이어졌는지(성공 응답·후속 행위) 따져 대응 우선순위를 정합니다.
핵심 관점 — SOC 분석은 "알림 개수"가 아니라 "조사 후 대응이 필요한가"로 판단합니다. 정찰(C)·정상업무(D)·방어성공(F)은 흔적이 남아도 대응이 불필요할 수 있습니다.

6Wazuh 실전 사용법

  1. 접속 — https://이_서버_IP → 계정 admin (비밀번호는 포털 상단에 표시).
  2. Discover 메뉴 → 좌측 상단에서 인덱스 패턴 선택:
    • wazuh-archives-* — 모든 로그(정상+이상). 기본 분석 대상.
    • wazuh-alerts-* — 룰에 걸린 탐지 알림만.
    • wazuh-alerts-*,wazuh-archives-* — 둘을 한 번에.
  3. 저장된 검색(상단 Open) — 🧩 전체 로그 / 🌐 웹 접근 / 🔐 인증 / 🧱 방화벽 / 🚨 탐지 알림을 열면 깔끔한 컬럼으로 바로 봅니다.
  4. 시간 범위 — 비어 보이면 우측 상단을 Last 1 year로 넓히세요(로그는 기준 시각 이전 24시간에 분포).

자주 쓰는 검색

data.srcip:"198.51.100.23"
full_log:"search.php"
rule.id:100101
full_log:"webshell_exec"
data.dstuser:"root"
location:"/var/log/ufw.log"
검색은 필드:값 형식입니다. 문자열은 full_log:"...", IP·계정은 data.srcip:"..."·data.dstuser:"...", 여러 조건은 and/or로 연결합니다.
⚠️ 대문자·특수문자(:)가 든 값은 따옴표 검색이 안 걸릴 수 있습니다. 이럴 땐 와일드카드를 쓰세요 — 예: full_log:*NOPASSWD*.

인덱스 패턴 — 어떤 로그를 볼지 고르는 '창'

인덱스 패턴은 Wazuh 인덱서(OpenSearch)에 쌓인 로그 묶음을 Discover에서 조회하도록 연결한 것입니다. 이 실습엔 3개가 준비돼 있습니다.

인덱스 패턴무엇을 보나
wazuh-archives-*모든 원문 로그(정상+이상) — 기본 분석 대상
wazuh-alerts-*룰에 걸린 탐지 알림만
wazuh-alerts-*,wazuh-archives-*둘을 한 번에 (난이도↑)

직접 만들려면 (목록에 없거나 새로 만들 때)

  1. 좌측 메뉴 ☰ → Dashboards Management(또는 Stack Management) → Index Patterns.
  2. Create index pattern 클릭 → 이름에 wazuh-archives-* 입력 (끝의 *로 날짜별 인덱스를 한 번에 묶음).
  3. 매칭되는 인덱스가 표시되면 Next step → Time field로 timestamp 선택 → Create index pattern.
  4. 이제 Discover 좌측 상단 드롭다운에서 그 패턴을 선택해 검색할 수 있습니다.
실습 환경엔 위 3개가 이미 생성돼 있어 Discover에서 선택만 하면 됩니다. 목록에 안 보일 때만 위 절차로 만드세요. (별표 *는 wazuh-archives-4.x-2026.08.13 같은 날짜별 인덱스를 한꺼번에 조회하기 위한 것)

DQL 검색 문법 (Discover 검색창)

Wazuh 대시보드는 DQL(Dashboards Query Language)로 검색합니다. 아래 문법만 알면 대부분의 분석이 됩니다.

문법의미예시
필드:값필드가 값과 일치rule.id:100101
필드:"문구"정확한 문구(공백 포함)full_log:"search.php"
and · or · not조건 결합 / 제외data.srcip:"198.51.100.23" and rule.level >= 10
* (와일드카드)부분 일치full_log:*NOPASSWD* · data.srcip:198.51.100.*
>= > <= <숫자 비교rule.level >= 7
필드:*필드가 존재하는 문서data.srcip:*

📑 이 실습의 주요 필드

필드뜻 · 쓰임
data.srcip출발지 IP — 공격자 추적의 핵심(피벗 기준)
data.srcuser · data.dstuser출발 / 대상 계정 (예: dstuser:"root")
rule.id탐지 룰 번호 (100101 등)
rule.level심각도 0~15 — 높을수록 위험(우선순위 선별에 유용)
rule.description룰 설명 문구
rule.groups룰 분류 (예: authentication_success)
location로그 원본 파일 경로 (어느 로그에서 왔는지)
full_log로그 원문 전체 — 가장 많이 검색하는 필드

실전 DQL 레시피

data.srcip:"198.51.100.23"
rule.id:100101 or rule.id:100102
rule.level >= 10
location:"/var/log/auth.log" and full_log:"Failed"
full_log:"search.php" and full_log:"cmd="
data.srcip:198.51.100.* and not rule.groups:authentication_success
full_log:*NOPASSWD*
location:"/var/log/ufw.log" and full_log:"BLOCK"
DQL 팁 — ① 대문자·특수문자(:)가 든 값은 full_log:*값* 와일드카드로. ② 탐지 알림만 볼 땐 wazuh-alerts-*, 전체 원문은 wazuh-archives-*. ③ 필드명이 헷갈리면 왼쪽 Available fields에서 필드를 클릭해 값 분포를 먼저 확인. ④ 결과가 이상하면 우측 상단 시간 범위(Last 1 year)부터 점검.

7실전 예제 — 웹셸 침해를 처음부터 끝까지 추적

알림 한 건에서 출발해 전체 공격 체인을 복원하는, 분석가의 실제 사고 흐름입니다.

  1. 알림에서 출발 — 탐지 알림에서 웹셸 명령 실행(rule.id 100101)이 보입니다. 먼저 이 알림들을 엽니다.
    rule.id:100101
    access.log에 GET /search.php?cmd=id 같은 요청이 있고, 출발지 IP가 198.51.100.23 임을 확인합니다.
  2. 공격자로 피벗(pivot) — 그 IP가 남긴 모든 흔적을 한 번에 모읍니다.
    data.srcip:"198.51.100.23"
    인증(auth)·웹(access)·감사(audit) 로그가 함께 나옵니다. 한 IP가 여러 로그 소스에 걸쳐 있다는 것 자체가 평범한 사용자와 다른 신호입니다.
  3. 최초 침투 확인 — auth.log에서 다수 Failed password 뒤 Accepted password for webadmin 을 찾습니다. 브루트포스가 성공한 그 시각이 침투 기점입니다.
  4. 실제 실행 여부 교차검증 — 웹 요청이 정말 실행됐는지 감사 로그로 확인합니다.
    full_log:"webshell_exec"
    comm="id"·comm="wget" 등 실행 프로세스가 보이고, 요청(access)과 실행(audit)의 시각이 일치하면 실제 실행이 확정됩니다.
  5. 후속 행위 추적 — 다운로드 → 지속성 → 유출로 이어집니다.
    full_log:"/tmp/.cache/kworker"
    full_log:"loot.tgz"
    wget 다운로드 → cron 반복 실행(지속성) → tar 압축 → curl 외부 업로드(198.51.100.47) 순서로 연결됩니다.
  6. 결론·대응 — 침투→명령실행→다운로드→지속성→권한상승→유출까지 동일 공격자의 단일 체인으로 재구성됩니다. 대응: 계정 잠금 · 웹셸 제거 · cron/sudoers 백도어 제거 · 유출 범위 확인.
분석의 뼈대 — ‘알림 1건 → 출발지로 피벗 → 여러 로그를 시간축으로 연결 → 실행 여부 교차검증’. 이 네 단계는 어떤 침해 분석에도 그대로 적용됩니다.

10주의점 & 오탐 판별 체크리스트

  • 시간 필터 함정 — 로그는 기준 시각(포털 상단) 이전 24시간에 분포합니다. Discover가 비면 시간 범위를 Last 1 year로.
  • 알림 ≠ 침해 — 미끼(C·D·F)도 알림/이상 로그를 남깁니다. 조사 후 대응 필요성으로 판단하세요.
  • 정상 속 이상 — 로그 대부분은 정상 트래픽입니다. 검색으로 좁혀 이상을 골라내세요(정상 200/304 사이의 cmd=, 정상 로그인 사이의 다수 Failed).
  • 안전한 실습 — 모든 공격 아티팩트(웹셸·백도어·변조 바이너리)는 실행되지 않는 더미입니다.
  • 답안 형식 — 포털의 "답안 형식"에 맞춰 입력(시각 HH:MM:SS, IP xxx.xxx.xxx.xxx). 오답은 감점, 힌트는 누적 감점(−1·−2·−3).

용어뜻
웹셸(web shell)웹서버에 올려두고 URL로 명령을 실행시키는 악성 스크립트. 여기선 비동작 더미.
브루트포스비밀번호를 반복 대입해 뚫는 공격. auth.log의 다수 Failed로 나타남.
지속성(persistence)재부팅·재접속에도 살아남게 하는 수법. cron·sudoers 등록 등.
권한 상승일반 권한에서 root 등 높은 권한을 획득. sudoers.d 백도어 등.
정보 유출(exfiltration)내부 데이터를 외부로 빼내는 것. 압축 후 외부 업로드.
미끼(decoy)공격처럼 보이지만 대응이 불필요한 사건(정찰·정상업무·방어성공).
SIEM여러 로그를 모아 상관분석·탐지하는 보안 관제 시스템(여기선 Wazuh).
피벗(pivot)하나의 단서(IP·계정)를 기준으로 관련 이벤트를 확장 조회하는 분석 기법.
